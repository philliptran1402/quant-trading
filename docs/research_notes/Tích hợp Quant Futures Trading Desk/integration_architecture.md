## What exists today, and what boundary should the Quant service have?

### Takeaway

Keep the Quant service as a deterministic research/backtest engine. Trading Desk API should remain the only browser-facing boundary and own user/team authorization, selecting/fetching market data, run metadata/results, and any later handoff to paper trading. For an MVP, use private synchronous HTTP from the NestJS API to a Python service; reserve NATS for market streams or later asynchronous job events, not a large candle-array RPC.

### Inferences

- Backtest input is bounded, batch-shaped data and the API needs an immediate result for the current “Run backtest” UI. A private HTTP call is the simplest MVP contract: it supports ordinary validation/error responses, keeps NATS out of the first Quant deployment change, and matches the current API-to-FTS style of private internal HTTP. This is a design recommendation, not an existing Quant capability. ([FTS private API convention](</Users/phitran/fublab/fts/README.md#L25-L36>); [NATS request-reply semantics](https://docs.nats.io/concepts/request-reply))
- Keep computation data-plane inputs explicit: API fetches the requested candle range, normalizes timestamp/interval/symbol/venue, and sends immutable OHLCV values plus a strategy ID/version and backtest configuration. The runner should not query Binance, hold exchange credentials, access account/private user data, or place orders in MVP. This isolates deterministic math and allows the same data snapshot to be replayed.
- The boundary contract should carry `schemaVersion`, `requestId`, venue/market type, symbol, interval, UTC start/end, candle data or immutable dataset reference, strategy ID/version/parameters, initial equity, position-sizing rule, fee model, slippage model, and explicit funding mode. The response should carry a run ID, status, metrics definitions, equity curve/trades, config echo, engine/strategy version, source and data hash, data coverage, warnings and cost diagnostics. Decimal-sensitive price/quantity/cash fields should be encoded as decimal strings; display metrics can use documented rounding.
- HTTP request/response is appropriate while one run completes within a bounded API deadline and request/candle payload limits. If runs become multi-symbol, parameter sweeps, optimization or long-running jobs, use `POST /backtests` to create a persisted run, return `202 + runId`, and have a worker publish progress/completion events; poll status or use SSE/WebSocket from the API. Do not keep a browser/API request open for an unbounded calculation. NATS supports request/reply, but its documentation recommends lightweight processing and timeouts; it is not a substitute for durable job state. ([NATS request-reply guidance](https://docs.nats.io/concepts/request-reply))
- NATS becomes useful if the runner later consumes live normalized data or publishes job lifecycle events. The current NATS deployment already connects the API and Gateway, so an internal subject can fit the deployment, but the Quant contract would still need schema/version compatibility, request IDs, timeout behavior, payload ceilings, retries/idempotency and authorization policy. For a historical candle RPC with potentially thousands of rows, HTTP is simpler; for asynchronous jobs, persist the job record first and use NATS/JetStream for dispatch/events rather than treating transient request/reply as durable work storage.
- Compose integration should follow one of three explicit packaging approaches: (1) install/build a versioned private Quant image and reference that image in Trading Desk Compose (portable/release-friendly); (2) place the service source in a coordinated `/Users/phitran/fublab` checkout layout so a relative Compose context works like FTS; or (3) provide a developer-only Compose override with an absolute local build context. Avoid silently relying on a path outside the repo checkout. ([Docker Compose build reference](https://docs.docker.com/reference/compose-file/build/); [FTS local Compose build context](</Users/phitran/fublab/trading-desk/devops-local/compose.api.yml#L75-L97>))

### Gaps

- The inspected market-data API retrieves Binance candles, but there is no inspected historical market-data storage/cache contract, data retention policy, dataset hash/version or historical funding endpoint. Current data freshness/revision policy therefore needs product/engineering decisions before reproducible research at scale.
- The current backtest's data fallback and strategy math have not been independently validated here for bar alignment, look-ahead bias, intrabar execution, liquidation, maintenance margin, or exchange-specific funding settlement. The current diagnostics only explicitly mark fees in and slippage/funding out. ([Advanced tools service, lines 33–63](</Users/phitran/fublab/trading-desk/api/src/advanced-tools/advanced-tools.service.ts#L33-L63>))
- The FTS-style token convention is a useful precedent, not an automatic solution for Quant. Production service identity rotation, TLS/network policies, secret storage, per-service least privilege and audit need a deployment decision. ([FTS README, lines 16–27](</Users/phitran/fublab/fts/README.md#L16-L27>))

## Which runtime, data ownership, identity, and persistence fit this repository?

### Takeaway

For MVP, implement one Python container around a normalized engine, with FastAPI/private HTTP. This reuses the Quant repo’s Python strategy source and is operationally isolated from the API, while avoiding the effort of translating algorithms to TypeScript or introducing a Rust strategy implementation. The Quant container should be stateless at first; Trading Desk API/PostgreSQL should own authenticated run records and UI access. If a first real strategy proves trivial and there is no need to reuse Python research code, an in-process Nest module would be cheaper; that is a valid alternative, but it does not create the requested language/dependency isolation.

### Cited Findings

- The Trading Desk API is a private NestJS 12/TypeScript service on Node 24, with Prisma/PostgreSQL and the `nats` JS client already among dependencies. ([API package.json, lines 1–18 and 19–38](</Users/phitran/fublab/trading-desk/api/package.json#L1-L38>))
- The Quant checkout consists of standalone Python scripts and project/data folders; its code guide records the absence of a common API/package structure and root dependency manifest. Existing files include dedicated MACD/RSI/Bollinger/Heikin-Ashi/Pair Trading backtests, alongside unrelated research projects. ([Quant code guide](</Users/phitran/phillip-tech-labs/quant-trading/docs/REPO_CODE_GUIDE.md>); [representative standalone backtest](</Users/phitran/phillip-tech-labs/quant-trading/MACD Oscillator backtest.py>))

### Inferences

- **Python service vs Nest module:** choose a Python service for the intended product because the reusable strategy material is Python and separate container dependencies let the API remain on its currently pinned Node stack. FastAPI provides a straightforward HTTP boundary. Tradeoff: another image, runtime, dependency lock, health checks, service token and observability surface. A Nest module minimizes deployment and auth plumbing, but duplicates/converts Python algorithms and couples CPU-heavy computations to API lifecycle. Rust is excellent for a later performance-critical, deterministic engine and already used in Gateway/FTS, but porting the current research code to Rust adds a rewrite before a benchmark shows need. For the first end-to-end prototype, a pure Python package/CLI can precede a service; separate the container only once a real, reusable strategy contract is chosen.
- **Identity:** Trading Desk API should authenticate the session, resolve team role and authorize access before it calls Quant. It sends a separate service credential/mTLS identity, correlation/request ID, and only the minimum necessary actor/run scope; it must not forward the user session token or exchange credentials. Quant is an internal compute service, not an identity provider. Because the checked Quant route currently ignores its principal and team access is single-team rather than workspace-aware, first decide whether Quant runs are private per user, visible to the single team, or account/workspace scoped. Make the API enforce the selected policy before adding storage or sharing.
- **Ownership:** API/PostgreSQL owns `backtest_run` records and access scope (`requestedBy`, optional team/workspace/account scope after that model exists), idempotency key/request hash, status, timestamps, immutable strategy/data/config references, and result location. Quant owns the algorithm registry and computation implementation/version, not user identity/ACL or trading ledger. If result payloads are large, persist them in object storage with API DB metadata/hash; do not expose arbitrary object references to users.
- **Strategy versioning:** Strategy ID/version/parameters are explicit immutable values in each run. Start with code-registered strategies rather than uploading/evaluating arbitrary user code. Record engine version and configuration hash so a result can be reproduced after strategy edits.
- **Database decision:** no Quant database is justified for bounded synchronous MVP runs. Persist result metadata and small summaries in Trading Desk DB if users need history; keep large equity/trade arrays in compressed JSON or object storage once size is measured. Add a Quant-owned DB only if the service later owns long-lived execution state, data snapshots, experiment queue/workers, or independently operated research datasets. Do not share Trading Desk Prisma tables directly from Python.
- **Auth gap prerequisite:** before storing user-visible run histories, add explicit team-role authorization to the quant route and ensure paper orders/history are scoped to the intended account/team model. Existing global session guard alone authenticates but does not establish that a specific caller is entitled to a particular result or account. ([AuthGuard](</Users/phitran/fublab/trading-desk/api/src/common/auth.guard.ts#L13-L31>); [Advanced tools service](</Users/phitran/fublab/trading-desk/api/src/advanced-tools/advanced-tools.service.ts#L25-L32>); [paper placement](</Users/phitran/fublab/trading-desk/api/src/paper-trading/paper-trading.service.ts#L221-L256>))
- **FTS boundary:** keep Fund Transport Service separate. Its documented responsibilities are transfer quote/workflow persistence and transfer idempotency/audit; it has its own PostgreSQL and internal bearer-token API. Strategy calculation, market-data normalization and paper execution are different domains, and mixing them would couple research lifecycle to funds permissions. ([FTS README, lines 1–3 and 25–44](</Users/phitran/fublab/fts/README.md#L1-L44>))

### Gaps

- The inspected Trading Desk schema and access code represent a private single-team deployment, not a general multi-workspace tenant model; a specific workspace schema/authorization design cannot be assumed from route names or the prior assessment.
- No production requirements were found for expected concurrent runs, maximum candle count, response-size limits, user-visible retention, execution latency or multi-venue support. These decide when to add a queue, database or data warehouse.
- The Nest API package already depends on NATS, but the Python Quant repo has no NATS integration today. If NATS is later selected for job dispatch, Python client/library support, contract generation, reconnect behavior and permissions need to be chosen and documented. NATS subject authorization is the broker-level mechanism to restrict publish/subscribe permissions. ([NATS authorization](https://docs.nats.io/learn/security/authorization))

## What should be built in each phase, and what must be true before backtest/paper progression?

### Takeaway

Build from a trustworthy single-strategy backtest, not a broad strategy marketplace or auto-trader. The minimum credible futures backtest needs a documented fill model and cost model, no synthetic fallback, reproducible input snapshots, and out-of-sample evaluation. Keep “strategy signal,” “paper order,” and “live order” as separate gates: paper integration should be explicit and pass through Trading Desk controls; live execution should remain a separate architecture/risk decision.

### Cited Findings

- The current Quant UI sends a backtest request and displays a result from the existing API but the current service's diagnostics state `feesIncluded: true`, `slippageIncluded: false`, and `fundingIncluded: false`; missing data is replaced by generated candles. A research report must not present that as a fully costed futures result. ([Advanced tools service, lines 33–63](</Users/phitran/fublab/trading-desk/api/src/advanced-tools/advanced-tools.service.ts#L33-L63>))
- Trading Desk's paper API already supports saved paper orders, fills, positions, cancellation, track record, and paper close paths. Its paper order placement uses mark price and a local fixed `PAPER_FEE_RATE`; the track-record provenance says unrealized PnL and funding are not included. This is a usable manual paper destination, but not a backtest simulator or an automated strategy scheduler. ([Paper controller, lines 16–90](</Users/phitran/fublab/trading-desk/api/src/paper-trading/paper-trading.controller.ts#L16-L90>); [paper service constants and placement, lines 9–20 and 221–256](</Users/phitran/fublab/trading-desk/api/src/paper-trading/paper-trading.service.ts#L9-L20>); [track-record provenance, lines 177–181](</Users/phitran/fublab/trading-desk/api/src/paper-trading/paper-trading.service.ts#L177-L181>))
- Gateway's market proto defines funding-rate updates, while the checked Quant backtest passes daily candles through a formula and reports funding excluded. A live current-rate stream does not supply the complete historical rate series required to replay historical funding charges. ([gateway.proto, lines 82–88](</Users/phitran/fublab/protos/gateway.proto#L82-L88>); [Advanced tools service, lines 33–63](</Users/phitran/fublab/trading-desk/api/src/advanced-tools/advanced-tools.service.ts#L33-L63>))
- Trading Desk’s proposed architecture says strategy runner outputs must go through OMS/Risk for trading requests and that historical market data/retention require an additional pipeline. The plan describes future design requirements and should be treated as proposals until code paths exist. ([Trading Desk README.vn.md, lines 59–67 and 85–99](</Users/phitran/fublab/trading-desk/README.vn.md#L59-L67>))

### Inferences

- **Phase 0 — product/data contract.** Choose one USDⓈ-M perpetual venue, one candle interval, one symbol, and one strategy. Define whether the UI control means exposure allocation or stop-risk budget; the current `riskPercent` input is not enough to infer stop-distance risk. Specify OHLCV schema, timestamp convention, candle completeness/gap policy, execution-at-next-open/close assumption, long/short/flat semantics, maker/taker fee, slippage, funding, leverage and return metric definitions. Do not call the current “Funding neutral” strategy implemented just because it appears in a selector.
- **Phase 1 — research engine package.** Refactor one strategy (for example MACD trend or Dual Thrust) as a pure function over normalized immutable data. Separate signal generation from portfolio simulation. Version it, make outputs deterministic, define no-look-ahead rules and document all assumptions. Add unit, property/regression, edge-case and leakage tests before treating performance as useful. (The test requirement here is a phase prerequisite recommendation, not a claim tests exist.)
- **Phase 2 — synchronous service integration.** Add one internal FastAPI container, private HTTP only, health/readiness endpoints, bounded payload and compute time, service credential, strict request/response schema. Trading Desk API validates caller/team access, fetches candles through its existing API-market-data adapter, calls the runner, stores a run summary/provenance, and returns it to Quant Lab. Errors for unavailable/insufficient data should fail closed; never manufacture candles. Keep API service routing and stored results under the existing auth boundary. This can follow the local FTS Compose pattern, but source/image packaging must be solved because the Quant repo is outside the fublab Compose tree. ([FTS service in local Compose](</Users/phitran/fublab/trading-desk/devops-local/compose.api.yml#L75-L97>); [Docker Compose build context behavior](https://docs.docker.com/reference/compose-file/build/))
- **Phase 3 — credible futures backtest.** Add historical funding-rate and mark/index series with coverage/provenance, venue fee schedules, spread/slippage model, tick/quantity filters, margin/leverage and maintenance/liquidation rules, partial-fill/stop semantics, and latency assumptions where relevant. Fetch/paginate consistently; persist data version/hash or snapshot if providers can revise history. Publish both gross and net performance and cost breakdown. This is needed before calling the result a high-fidelity futures simulation; a daily candle engine cannot establish intrabar liquidation or stop execution.
- **Phase 4 — evaluation and paper-forward path.** Require in-sample/out-of-sample split, walk-forward/rolling evaluation, benchmark, sensitivity to costs/parameters, drawdown/stability, and a predeclared paper duration/trade count. Emit signal records with strategy version and timestamps. A user or authorized operator can explicitly turn a signal into a paper order through the Trading Desk paper API. Compare signal price/decision to paper fill, fees, funding and mark; add duplicate-signal idempotency, stale-data handling, stop/kill controls and audit. Do not let the runner call `PaperTradingService`/Gateway directly; the existing API layer should retain authorization and a potential OMS/Risk boundary.
- **Phase 5 — async research workloads.** Only after synchronous runs prove too slow or need sweeps, add persistent job state (`QUEUED/RUNNING/SUCCEEDED/FAILED/CANCELED`), queue/worker concurrency limits, cancellation, retries/idempotency, progress events, result retention and status retrieval. At this point NATS/JetStream can dispatch work/events, with durable storage authoritative for job status. Core NATS request/reply can remain for light synchronous calls or service discovery, not as the only record that a long job exists. ([NATS request-reply guidance](https://docs.nats.io/concepts/request-reply))
- **Phase 6 — optional live execution proposal.** Treat this as a separate explicit approval and architecture review. Runner should emit versioned intent only. API/OMS/Risk checks limits and account policy, then execution crosses a versioned Gateway contract; idempotency, reconciliation, kill switch, audit and canary are prerequisites. FTS remains isolated and is not in the order path. This is consistent with Trading Desk’s documented Strategy Runner → OMS → Gateway direction, but that document is architectural guidance, not proof those complete components exist. ([Trading Desk README.vn.md, lines 36–67 and 85–107](</Users/phitran/fublab/trading-desk/README.vn.md#L36-L67>))
- **Choice of runtime by phase:** Python/FastAPI for MVP and reusable Quant research; TypeScript/Nest module only for a deliberately small proof where source reuse is not a priority; Rust only if profiling later shows calculation throughput, memory, or a strong shared Rust domain contract justifies rewriting. Keep one engine/contract regardless of runtime, and do not deploy one service per strategy.

### Gaps

- No evidence was found that there is already a dedicated OMS/Risk service, historical candle archive, backtest dataset store, full risk-control engine, strategy scheduler, or live runner. README architecture and PLAN material should be labeled as proposed until implemented and independently verified. ([Trading Desk README.vn.md, lines 32–67](</Users/phitran/fublab/trading-desk/README.vn.md#L32-L67>); [current API root module](</Users/phitran/fublab/trading-desk/api/src/app.module.ts#L21-L44>))
- The source review did not establish exchange-specific historical funding coverage, exact mark-price history availability, maker/taker tiers for the intended paper/live account, or fill/slippage calibration data. These are Phase 0/3 decisions and must not be replaced by a single hard-coded fee/funding guess.
- No chosen initial strategy, interval, contract size, start capital, leverage constraints, risk budget, benchmark or acceptance thresholds were specified. These are required to turn the phase outline into an implementation spec.
